## Headless methodology — what worked, and what didn't (read this before the results)

**`claude -p --session-id X ...` then later `claude -p --resume X ...` does
NOT preserve the read-signal watermark across the two invocations.** Each
invocation is a separate OS process, and print-mode's own process exits at
the end of one turn — so `--resume` for a second turn necessarily spawns a
**new** `strata-mcp` server process (a new PID) that reconnects to the
**same** `STRATA_AGENT_SESSION_ID`. The engine's own `record_connect`
(`session_state.py`) correctly treats a same-id-different-pid reconnect as a
legitimate "this id is being reused" case (built for crash recovery) and
**rolls the prior state over** to `<id>.rolled-N.json`, starting the counters
fresh:

```
# After turn 1 (clean read, watermark recorded):
{"session_id": "evidence-session-A", "reads": 1, "declines": 1,
 "reads_by_scope": {"g_root": {"count": 1, "watermark": "g_root:v0|op:g_root:-|ce:g_root:0:-"}},
 "server_pid": 602488, "ended_at": "2026-10-03T12:06:42..."}

# After `claude -p --resume <same claude session id> ...` for turn 2:
{"session_id": "evidence-session-A", "reads": 0, "declines": 0,
 "reads_by_scope": {}, "server_pid": 603185, "ended_at": "2026-10-03T12:07:35..."}
# -- turn 1's state archived verbatim to evidence-session-A.rolled-1.json
```

This is not a bug: it is the documented behaviour of
`SessionStateStore.record_connect` ("if a record already exists from an
EARLIER connection (a different server pid)... a fresh record starts"),
correctly applied — print-mode's one-process-per-invocation model is just
not the shape that assumption was written for. **An actually interactive
Claude Code session (the long-lived case this feature exists for) never
hits this**, because its one MCP server process stays up for the whole
session; only the process-per-invocation shape of `claude -p [--resume]`
does.

**What worked:** feeding Session A's turns to **one, continuously-running**
`claude -p --input-format stream-json --output-format stream-json` process
over a named pipe (so one MCP server, one PID, for the whole scenario),
pausing between turns (by holding stdin open) to run Session B's separate,
ordinary `claude -p` invocation and check it landed before sending the next
turn. This is a genuine real-harness run — real tool calls, real judge
calls, real Stop hook — just driven over stdin instead of three independent
`--resume` calls, which the finding above rules out as a way to preserve
same-session state headlessly. `--max-budget-usd` was tried once and
removed: it caps Claude's own API cost, not the judge key, and a single
ordinary turn with this project's tool/skill set already costs ~$0.05–0.25
in Claude's own usage — the wrong lever for the judge-key budget this run
is actually about.

## Scenario and results

**Session A** (`STRATA_AGENT_SESSION_ID=evidence-session-A`, claude session
`06ef71d8-d13c-4822-9d29-a7bf5f3d17fe`), **Session B**
(`evidence-session-B`, contributes), both against scope `g_root`.

### Turn 1 — Session A reads

Prompt: *"Read your perspective with strata_read_perspective, then stop."*

State after:
```json
{"session_id": "evidence-session-A", "reads": 1, "declines": 1,
 "reads_by_scope": {"g_root": {"count": 1, "last_read_at": "2026-10-03T12:12:10.216279+00:00",
   "watermark": "g_root:v0|op:g_root:-|ce:g_root:0:-"}},
 "ended_at": "", "server_pid": 611651, "strict": false}
```
Receipt watermark recorded: `g_root:v0|op:g_root:-|ce:g_root:0:-`. (The
assistant also called `strata_session_closeout` unprompted — the harness's
own instinct, not something asked for; harmless.)

### Session B contributes

Prompt: *"Contribute this short context note via strata_contribute,
classified as context: 'The team prefers tabs over spaces for this
throwaway test.' Then stop."*

Judged and accepted: `{"contribution_id": "c_0314acbc836b01cf", "judgment":
{"decision": "accept_as_context", "summary_updated": true}}`. `g_root`'s
summary moved from version 0 to version 1.

### Turn 2 — Session A calls `strata_list_scopes` (default/non-strict mode)

Prompt: *"Call strata_list_scopes, then stop."*

**(a) Raw tool-result JSON** — the actual MCP tool result Session A received,
verbatim:
```json
{
  "strata": [{"id": "L0", "name": "root", "ordinal": 0}],
  "scopes": [{"id": "g_root", "name": "Root", "stratum_id": "L0", "status": "active",
    "default_skill": "strata-worker", "permitted_skills": null,
    "description": "A scratch scope for a live #234 read-signaling evidence run; nothing of substance"}],
  "edges": [],
  "perspective_stale": ["g_root"]
}
```
`perspective_stale: ["g_root"]` is present — confirmed.

**(b) Stop hook, default mode — a non-blocking notify.** The transcript
carries a `system`/`informational` event, not a block:
```json
{"type": "system", "subtype": "informational",
 "content": "Stop says: Memory you read has changed since you read it; re-read before acting. Affected scope(s): g_root.",
 "level": "notice"}
```
The assistant's own turn ended normally right after (`stop_reason:
"end_turn"`) — nothing blocked it. State file: `"read_signal_notified":
true, "strict_blocks": 0`.

### Turn 2, repeated under strict mode — a block

Separate run, `STRATA_AGENT_SESSION_ID=evidence-session-STRICT`, claude
session `a1553f83-48a4-4652-b8df-1803acf0ed8d`, `STRATA_FRESHNESS_STRICT=1`.
Session STRICT read perspective (watermark `g_root:v2|...`), then a second
contributing session (`evidence-session-E`) pushed `g_root` to version 3,
then Session STRICT called `strata_list_scopes` — same `perspective_stale:
["g_root"]` result — and this time the turn did **not** end there. The
transcript shows a synthetic blocking message injected before the turn
could finish:
```json
{"type": "user", "message": {"role": "user", "content": [{"type": "text",
  "text": "Stop hook feedback:\nMemory you read has changed since you read it; re-read before acting. Affected scope(s): g_root."}]},
 "isSynthetic": true}
```
forcing the assistant to call `strata_read_perspective` again (now seeing
version 3) before the turn was allowed to end. State file confirms exactly
**one** block:
```json
{"strict": true, "strict_blocked_at": "2026-10-03T12:17:15.501465+00:00",
 "strict_blocks": 1, "read_signal_notified": true, "tool_calls_at_last_block": 3}
```
A `system`/`notification` line (`"stop-hook-error", "text": "Stop hook error
occurred · ctrl+o to see"`) also appeared alongside the block in the
transcript — Claude Code's own UI surfacing that a hook returned a blocking
decision; included here for completeness, not independently verified
beyond what the transcript shows.

### Turn 3 — Session A re-reads, then calls `strata_list_scopes` again

Prompt (same running Session A process as turns 1–2): *"Read your
perspective with strata_read_perspective again, then call
strata_list_scopes, then stop."*

The re-read shows `g_root` at version 1 with the new content. The
subsequent `strata_list_scopes` result carries **no** `perspective_stale`
key at all, and no Stop-hook clause fired this turn — matching the
expectation exactly: once a session has re-read the scope that moved, it is
no longer reported stale.

### (d) Self-trigger — a session's own contribution doesn't mark it stale

Separate session (`evidence-session-D`), one turn: *"First, read your
perspective... Then contribute this short context note... Then call
strata_list_scopes. Then stop."* The contribution was judged and accepted
(`c_c76cb8f49e415251`, `g_root` version 0 → 2 in this fresh project copy),
and the immediately-following `strata_list_scopes` result carries **no**
`perspective_stale` field — the session's own write advanced its own
receipt watermark (`g_root:v2|...`), so it is not told its own change is
news to it. State file: `"contributions": 1, "submitted": 1,
"read_signal_notified": false`.
