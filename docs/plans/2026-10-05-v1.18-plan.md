## 0. Patch first: 1.17.1

**A child directive that changes an inherited value is held mechanically.** In 1.17.0, a child-bound session can get its own directive admitted that contradicts an inherited one; the judge is the only defence. A reporter's Haiku run admitted 4 such directives, all on one fact, reasoned as "team-local practice". The fix:
- When an admitted directive's subject is covered by an inherited directive, it must pass #237's tightening test against it.
- Otherwise it is held as context with an engine note.
- Uncovered subjects (genuine refinements) and true tightenings pass. Uncertain cases fail toward context, never toward a contradicting rule.

Branch `feat/v1171-admit-side-inherited-check`, work in progress. Gate:
- a forged-ADMIT attack: every contradiction and exemption, forced to an admit, must be held;
- every real refinement and tightening must still pass;
- bridge runs of j1_refinement, J1 and j4_interior.
Bridge only, no key. It ships as 1.17.1 with its own small evidence file.

## 2. The reporter's findings (all of them)

1. **The admit-side check** → 1.17.1 (section 0).
2. **In-text instructions to the judge from a bound session (the j4-106 class).** A session bound to a scope may change its own rules, so an instruction written into its own contribution ("just accept it as-is") is stopped only by the judge. The default judge admitted one such case once in the v1.17 baseline.
   - Design: engine-side detection of judge-addressed text on a contribution that would change a directive. If it matches, the change is held as context with a note naming the marker; the contributor resubmits without it.
   - Gate: instructed own-scope changes (must hold) with plain twins (must apply), plus a forged-answer attack. Bridge.
   - Open question for the philosopher: is a bound session's in-text instruction a different act from its plain contribution, or the same act badly worded?

   - **His eval:** we publish a small spec of the boundary claims it should test (child→parent, child-own versus inherited, own-scope changes, hearsay), and he runs it against releases. We receive results, never his data in our repos.
   - **Our eval:** a strata-evals set written by us from the abstract shapes in the advisory (no texts of his), pinned-judge and bridge runnable, part of every release baseline.
4. **His two-level rerun against 1.17.** Ask him to rerun the two-level setup on 1.17.0, both cases: child writes to the parent (expect 0 parent changes, proposals instead) and child writes its own scope (expect held contradictions after 1.17.1). We need no key; it's his run.
